# المعمارية العامة — ANIXOS

هذا الملف يوثِّق القرارات المعمارية **كما نُفِّذت فعلياً**، وسبب كل قرار، وما هو مكتمل مقابل ما هو مخطَّط له فقط.

## 1) المكدس التقني

| الطبقة | التقنية | لماذا |
|---|---|---|
| Frontend | React 19 + TypeScript + Vite | يُبنى مرة واحدة كتطبيق ويب، يُغلَّف لاحقاً بـ Electron (Desktop) وCapacitor (Android) بدون إعادة كتابة |
| التنسيق | Tailwind CSS v4 | عبر `@tailwindcss/postcss`؛ الواجهة بأكملها RTL افتراضياً (`index.html` بـ `dir="rtl"`) |
| Backend | Supabase (PostgreSQL + Auth + Realtime + Edge Functions) | بديل كامل عن خادم Express تقليدي؛ RLS يحل محل طبقة تفويض API منفصلة |
| التخزين المحلي | Dexie.js (IndexedDB) | الخيار الوحيد الذي يعمل بنفس الكود على الويب/Electron/Capacitor؛ ملفات JSON محلية (المخطط الأول المقترح) كانت لتفشل على Capacitor |
| المنطق الحساس | Supabase Edge Functions (Deno) | كل عملية تتطلب `service_role` أو ذرّية عبر عدة جداول |

## 2) العزل بين الشركات (Multi-Tenant)

**لا يوجد "مدير مستأجرين" (TenantManager) مخصَّص في الكود.** العزل بالكامل على مستوى قاعدة البيانات:
- عمود `company_id` على كل جدول تقريباً.
- دالة مركزية واحدة `get_my_company_id()` (`SECURITY DEFINER`) تُستخدَم في كل سياسات RLS.
- تدعم الدالة حالتين: موظف إداري (`staff_users`) أو جهاز Kiosk (`devices.auth_user_id`).

هذا أبسط وأصعب اختراقاً من طبقة تطبيقية منفصلة، لأن العزل يُفرَض حتى لو استُدعيت قاعدة البيانات مباشرة متجاوزةً كود التطبيق بالكامل. **تم اختبار هذا فعلياً**: محاولة إدخال بيانات باسم شركة أخرى تُرفض بخطأ `permission denied` من PostgreSQL نفسه، وليس من كود JavaScript.

## 3) هوية الأجهزة والعمال — أهم قرار معماري في المشروع

المشكلة الأصلية: العامل يحتاج دخولاً بسيطاً (اسم مستخدم + كلمة سر أو RFID) بلا تعقيد حساب Auth كامل، لكن قاعدة البيانات (عبر RLS) تحتاج **هوية موثوقة** لتحديد `company_id`.

**الحل المُنفَّذ**:
- **الجهاز نفسه** (كشك ثابت) يحصل على حساب Supabase Auth تقني دائم عند تسجيله (`register-device` + `devices.auth_user_id`)، ويبقى مسجَّل الدخول به إلى الأبد على ذلك الجهاز تحديداً.
- **العامل** يُسجِّل دخوله فوق تلك الجلسة عبر جلسة منطقية (Application-Level Session) لا علاقة لها بـ Supabase Auth، تُتحقَّق عبر `worker-login` Edge Function (بحماية Brute-Force: قفل 15 دقيقة بعد 5 محاولات فاشلة).
- **دعم أوفلاين كامل**: `kiosk-credentials-sync` يُحمِّل نسخة `bcrypt hash` من كلمات سر عمال الشركة إلى الجهاز (`localDb.workerCredentials`) أثناء الاتصال، لتُستخدَم للتحقق المحلي (`bcryptjs` في المتصفح) عند انقطاع الإنترنت الكامل — مع قفل محلي مطابق (15 دقيقة/5 محاولات).
- **حماية إضافية صارمة**: عمود `workers.password_hash` غير قابل للقراءة إطلاقاً عبر دور `authenticated` العادي (`REVOKE`/`GRANT` على مستوى الأعمدة، وليس فقط RLS على مستوى الصفوف) — فقط `service_role` داخل Edge Functions يصل إليه، وفقط لجهاز Kiosk مُسجَّل فعلياً (يُتحقَّق من `devices.device_mode = 'kiosk'` صراحة داخل `kiosk-credentials-sync`، وليس فقط من `company_id` المتطابق).

## 4) استراتيجية العمل بلا اتصال (Offline-First)

كل كتابة في الكشك (`switchWorkerSession`, `markPieceTaskComplete`, تسجيل الدخول) تتبع نمطاً موحَّداً:
1. تُكتَب محلياً في Dexie فوراً (استجابة لمسية فورية بلا أي تأخير شبكي محسوس).
2. إن كان متصلاً: تُرسَل مباشرة لـ Supabase.
3. إن كان منقطعاً (أو فشل الإرسال رغم الاتصال الظاهري): تدخل `syncQueue` (جدول Dexie منفصل).
4. `syncEngine.ts` يُفرِّغ الطابور تلقائياً عند عودة الاتصال (مراقبة حقيقية عبر Heartbeat فعلي لـ Supabase، وليس فقط `navigator.onLine` غير الموثوق كلياً)، بمحاولات متكررة وعدم فقدان أي سجل عند الفشل المتكرر.
5. **Idempotent Retry**: كل معرّف (`id`) يُولَّد على العميل (`crypto.randomUUID()`) قبل الإرسال، فإعادة المحاولة بعد فشل جزئي لا تُنشئ تكراراً (`upsert` وليس `insert`).

## 5) دورة العمل المترابطة (Order-to-Cash + Shop Floor)

راجع `docs/ERD.md` قسم 3-6 للتفصيل الكامل. الخلاصة المعمارية: الربط بين "قبول عرض سعر" و"إنشاء مشروع + أمر تصنيع" و"إصدار فاتورة" يتم عبر **Edge Functions ذرّية** (`accept-quote`, `generate-invoice`) بتراجع يدوي كامل (Manual Rollback) عند فشل أي خطوة وسطى — وليس عبر معاملات SQL حقيقية (Postgres transactions) لأن كل خطوة قد تستدعي منطقاً مختلفاً عبر REST API منفصلة. أما الربط بين "إنجاز قطعة في الكشك" و"اكتمال المشروع تلقائياً" فيتم عبر **Trigger حقيقي في قاعدة البيانات** (`recalc_completion_after_piece_update`) لأنه منطق بيانات بحت لا يحتاج طبقة تطبيقية.

## 6) ما هو مكتمل ومُختبَر فعلياً مقابل ما هو مخطَّط فقط

### مكتمل ومُختبَر (على قاعدة PostgreSQL حقيقية + `tsc`/`vite build` ناجحين)
- 27 migration، كل الجداول والعلاقات والمحفزات والViews
- 7 Edge Functions
- واجهة الكشك الكاملة (أونلاين + أوفلاين)
- معالج الإعداد الأولي وتسجيل الأجهزة
- كل الأقسام الإدارية: لوحة المدير، المخطط، المشاريع، أوامر التصنيع، المبيعات، المخزون، العملاء، الموارد، الأرشيف
- دورة الربط الكاملة: عرض سعر → مشروع → أمر تصنيع → تنفيذ → إكمال تلقائي → تقرير → فاتورة → أرشفة

### مخطَّط فقط (لم يُبنَ بعد)
- تطبيقا Electron وCapacitor الفعليان (المجلدات غير موجودة بعد؛ الكود المصدري في `apps/web` جاهز كأساس لهما)
- تكامل Odoo الفعلي (جدول `odoo_config` جاهز، لا توجد Edge Functions للمزامنة الفعلية بعد)
- تطبيق `hasPermission()` على مستوى واجهة المستخدم (راجع `docs/RBAC_matrix.md`)
- منتقي كامل للآلة/المشروع من داخل الكشك (حالياً زر "تغيير" يُصفِّر القيمة فقط تمهيداً لاختيار يدوي)
- قسم الهندسة (رسومات فنية، مواصفات تفصيلية)
- بوابة العميل (متابعة الطلبات، `clients.portal_auth_user_id` جاهز في قاعدة البيانات لكن بلا واجهة)
